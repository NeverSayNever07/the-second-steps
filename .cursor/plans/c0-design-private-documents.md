## What the code already gives us (inspected 2026-10-20)

- Every app transaction sets `app.workspace_id`, `app.membership_id` and branch scope with transaction-local `set_config` (`core/access/data/database-context.ts`). RLS on every tenant table reads those settings.
- Instruction tables follow one pattern (`20261017120000_instructions_and_terms`): workspace-aware composite foreign keys, history rows that are added and never edited, database times, `*_check_instruction` triggers, role helper functions such as `instruction_member_can_work(membership, branch)`, and grants of `SELECT, INSERT` (plus `UPDATE` only where a row has allowed changes), never `DELETE`.
- Permissions are code-defined (`core/access/domain/permission.ts`, `role.ts`); the database enforces the same roles through helper functions.
- `audit_events` records actor, workspace, action, outcome, target and request id.
- The server already holds `SUPABASE_SECRET_KEY` (`core/auth/supabase-admin.ts`) and `@supabase/supabase-js`, which includes the Storage client. **No new dependency is needed.**
- Integration tests run against a disposable local PostgreSQL with no Supabase Storage.

Two findings shape the design:

1. **Accounts holds `property.update`.** The owner decided Accounts cannot change compliance, so compliance needs its own permission rather than reusing `property.update`.
2. **The proxy buffers at most 10 MB of a request body** (`proxy.ts` matches every route; Next.js `proxyClientMaxBodySize` default). A 10 MB file plus multipart overhead would be truncated. Server Actions are limited to 1 MB unless the limit is raised for every action.

## Upload lifecycle and failure cleanup (no queue)

Each upload is one request:

1. From the query parameters and headers only: verify session, the workspace's MFA rule, origin, content type and declared size; load the access context from the workspace slug; check the permission for the target record (C2: `instruction.manage` on that instruction; C3: `property.compliance.manage` on that property).
2. Read the capped body; detect type; check size, encryption and the kind's allowed types; compute SHA-256.
3. **Transaction 1:** insert a `documents` row with status `pending`. RLS and triggers recheck workspace, branch and role, and that the linked instruction is still current. Commit.
4. Upload the bytes to Storage at the row's object key with `upsert: false` (an existing object is never overwritten).
5. **Transaction 2:** conditionally mark the row `stored` (only while it is still `pending`) and create the business link (agreement draft or compliance evidence) in the same transaction. Audit success.
6. **Failures always change the row first and delete the file second.** On failure at 4: conditionally mark the row `failed` (`WHERE status = 'pending'`). On failure at 5, or if its result is unknown (for example a lost reply): re-read the row. If it is `stored`, the upload succeeded and nothing is deleted. If it is still `pending`, conditionally mark it `failed`, commit, then delete the object. If it is already `failed` (cleanup got there first), delete the object.
7. Failure and refusal audit events are written in their own transaction, so they survive the rollback of the work that failed. They carry a reason code, never file content or the display name.

If the process stops between steps, a row stays `pending`. Because the row is always written before the object, an object without a row can only come from tampering.

- **Opportunistic cleanup:** at the start of each upload, the server runs one conditional update that marks that workspace's `pending` rows older than one hour by database time, **for records the uploader can work on**, as `failed` (`failure_code = 'abandoned'`), and returns the rows it actually changed. It commits, then deletes the objects for those rows only. A slow upload that finishes first is `stored` and is left alone; one that finishes after is refused at step 5 and removes its own object under step 6. No privileged system actor is needed.
- **Reconciliation report:** an owner-run read-only script lists, for one workspace, `pending` rows, objects with no row, and `stored` rows with no object. Used in C1 tests and the C5 checkpoint.
- **Draft removal (C2/C3):** a `stored` file still in draft use may move to `removed` with a reason, actor and audit event; its object is deleted after the row commits. The C2/C3 triggers refuse removal once the file backs a completed agreement or relied-on evidence.

## C1 migration — `documents`

```
enum document_kind:   instruction_agreement | compliance_evidence
enum document_media:  pdf | jpeg | png
enum document_status: pending | stored | failed | removed

documents
  id                         uuid pk
  workspace_id               uuid not null, unique (workspace_id, id)
  kind                       document_kind
  instruction_id             uuid null  → instructions (workspace_id, id)
  property_id                uuid null  → properties (workspace_id, id)
  display_name               varchar(120)
  media_type                 document_media
  byte_size                  int check 1..10485760
  sha256                     char(64) check lower-case hex
  status                     document_status default 'pending'
  failure_code               varchar(40) null
  removal_reason             varchar(500) null
  uploaded_by_membership_id  uuid → memberships (workspace_id, id)
  removed_by_membership_id   uuid null → memberships (workspace_id, id)
  created_at, stored_at, ended_at   timestamptz, set by the database

checks
  instruction_agreement ⇒ instruction_id set, property_id null, media_type = pdf
  compliance_evidence   ⇒ property_id set, instruction_id null
  status/time/actor columns agree (stored ⇒ stored_at; removed ⇒ reason, actor, ended_at; failed ⇒ failure_code, ended_at)
indexes: (workspace_id, instruction_id), (workspace_id, property_id), (workspace_id, status, created_at), actor columns
```

**Triggers:** every column except `status`, `failure_code`, `removal_reason`, `removed_by_membership_id` and the database times is fixed after insert. Insert must be `pending`, uploaded by the current membership. Times come from the database. Each status change has its own rule (review finding 4):

| Change             | Who                                                 | Extra condition                                                                                    |
| ------------------ | --------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `pending → stored` | the uploader only                                   | the linked instruction is still current (locked `FOR SHARE`, as `prepare_instruction_record` does) |
| `pending → failed` | the uploader, any reason code                       | —                                                                                                  |
| `pending → failed` | another member who can work on the record           | only `failure_code = 'abandoned'` and the row is more than one hour old by database time           |
| `stored → removed` | `removed_by_membership_id` = the current membership | reason required; C2/C3 add "not backing completed or relied-on evidence"                           |

Any other change is refused. Insert also applies the instruction lock and the "still current" check.

**RLS (enabled and forced):**

- _Select:_ workspace matches; the caller holds an **active staff membership** (any of the seven staff roles, checked with the existing `instruction_member_has_role` helper); and the linked instruction (agreements) or property (compliance) is visible to the caller. Those tables' own RLS supplies branch scope, so every staff role that can read the record can see its files (owner decisions 13 and 27). The staff-role condition changes nothing today. It stops a future landlord, contractor or participant who can see a property or instruction from gaining its files without an explicit document grant (review finding 5).
- _Insert:_ workspace matches, the uploader is the current membership, and the caller can work on the linked record: `instruction_member_can_work(…, instruction branch)` for agreements; a new `property_compliance_member_can_work(…, property branch)` for compliance (Account Owner, Agency Admin, Branch Manager, Negotiator, Property Manager).
- _Update:_ separate `USING` and `WITH CHECK` clauses (the `instruction_party_update_in_scope` pattern): the row is visible and the caller can work on its linked record. The trigger above decides which change that member may make.

**Grants:** `SELECT, INSERT` and column-level `UPDATE` on only `status`, `failure_code`, `removal_reason` and `removed_by_membership_id` to `zayto_app`; `DELETE, TRUNCATE` revoked. Rows are never deleted by the app.

**Branch moves:** compliance files follow the property's current branch. Agreement files follow the instruction's branch, which cannot change while the instruction is current. After an instruction ends and the property moves branch, the old branch keeps seeing that instruction and its agreement, and the new branch does not, exactly as for the instruction itself.

**Permission:** add `property.compliance.manage` to Account Owner, Agency Admin, Branch Manager, Negotiator and Property Manager in `role.ts` (and the matching database helper). Agreements reuse `instruction.read` / `instruction.manage` (owner decisions 13 and 14). C1 adds the permission and helper so the table's policy is complete; nothing uses it until C3.

**Audit actions:** `document.upload` (success/failure with reason code), `document.download` (success/refused), `document.integrity_mismatch`, `document.remove`, `document.abandoned`. Metadata holds document id, kind, size and media type, never content or the display name.

## Code shape (C1)

- `core/documents/domain/` — file sniffing, encryption check, display-name sanitising, size limits; pure functions with unit tests.
- `core/documents/application/` — upload and download services that take a `DocumentStore` interface.
- `core/documents/data/supabase-store.ts` (server-only) — the one place the secret key touches Storage; an in-memory `DocumentStore` for integration tests.
- `app/dashboard/w/[workspaceSlug]/documents/upload/route.ts` and `app/dashboard/w/[workspaceSlug]/documents/[documentId]/route.ts` — thin handlers that return JSON errors, never redirects.
- **Download headers** (the proxy skips the route, and a test asserts the matcher excludes both document routes): `Content-Type` from the stored media type, `Content-Disposition: attachment`, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Content-Length` from the verified size.

## C1 tests

- **Unit:** each file type accepted and rejected (wrong magic, truncated, renamed extension, encrypted PDF, over 10 MB, empty), display-name cases.
- **Integration (local PostgreSQL + in-memory store):** cross-workspace and cross-branch reads and inserts refused; Accounts and Read Only cannot upload; every staff role that can read the record can download; changing a document id in the URL to another workspace's or an unseen branch's file is refused, including for a member of both workspaces using the other workspace's slug; MFA-pending sessions refused; fixed columns and each disallowed status change refused, including a colleague marking a fresh upload failed; no delete grant; nothing attaches to an ended instruction; only `stored` files download; object substitution (stored bytes changed) refused before any byte is sent; failed Storage upload leaves `failed` and no object; failure after the object leaves no orphan; a lost commit reply never deletes a stored file (the code path re-reads the row first; not reproducible in an automated test, so **unverified**); cleanup racing a slow upload never leaves a stored row without its file; missing or wrong `Origin`, missing `X-Zayto-Upload`, wrong content type and over-size bodies refused; the proxy matcher excludes the upload route; `rls-coverage` and `database-grants` updated.
- **Manual smoke test against the shared development bucket** after owner approval: upload, download, refused direct access with a user token. This stays **unverified** in automated tests because CI has no Supabase Storage.

## C2 and C3 outline (designed fully before their migrations)

- **C2 `instruction_agreements`:** draft → completed → superseded; links one stored PDF, the exact terms version and a snapshot of required signing parties; signed/completed date required, never in the future; completed rows immutable; a replacement links the agreement it supersedes. The Ready to market checklist moves from `instruction_agreement_events` to "a completed agreement whose material terms and parties match the current ones", and the agreement exception stops counting. Existing events stay as history.
  - **To confirm at C2:** which current terms fields are material. The plan names service, fees, VAT treatment, landlord parties and allocated responsibilities. That would mean an asking-rent or deposit change does **not** require a new agreement. Responsibilities are not captured in terms yet.
- **C3 compliance:** one item per property and area (five areas); applicability and evidence-status history rows (added, never edited); evidence events linking `compliance_evidence` documents, with one marked as relied on; staff-entered dates only.

## Not covered and still unverified

- Malware scanning and quarantine (deferred; controlled fictional files only, shown in the interface).
- Rate limiting and per-member upload quotas (not implemented anywhere yet); the size cap and authentication-before-read limit abuse for the internal fictional MVP. Storage use is a cost and availability risk on a small plan before real use.
- A Storage-only secret key that can be rotated separately from the sign-in key (real-data item).
- Active content inside PDFs (real-data item, with scanning).
- Image metadata (for example photo location data) is kept as uploaded; stripping it is a real-data item.
- Whether the shared project already has a `storage.objects` policy granting `authenticated`: the bucket script reports it; until it has run, this is unverified.
